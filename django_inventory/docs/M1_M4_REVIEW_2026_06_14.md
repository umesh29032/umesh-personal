## Reading the raw output honestly
Reviewers returned **M-1 NO_GO · M-2 NO_GO · M-3 NO_GO · M-4 GO-WITH-CHANGES**. The

## A. Genuine contradictions (addendum premise wrong vs shipped code — fix the DESIGN before S4 code)

**C1 — `AddaProductSizeColorPieceBreakdown` is NOT a "dead snapshot (0 consumers)" (M2-1, CRITICAL, upheld high).**
The addendum's M-1/M-2 premise — "it's a dead snapshot, 0 consumers, safe to generalize
into StagePoolSnapshot" — is **false against the code**. `barcode_generation/assembly.py:
generate_from_breakdown` reads it at runtime (BarcodeBatch ranges), called from
`barcode_generation/service.py:263`; `cutting/service.py` writes it. → "Generalize it into
StagePoolSnapshot" is **not an inert refactor** — it touches a live barcode path.
**Change:** S4 must either (a) leave `AddaProductSizeColorPieceBreakdown` as the
Cutting-specific artifact and build `StagePoolSnapshot` as a **new** parallel table, or
(b) migrate the barcode consumer too — explicitly, with tests. The addendum's "reuse this
snapshot" framing must be rewritten.

**C2 — Settlement-first means there is NO allocation row before settlement (M2-2/M2-6, CRITICAL→high, upheld).**
M-2's pool draw-down happens at **complete** (pre-settlement). But `StageWorkAssignment`
(the only allocation-shaped row) is **born at settlement-finalize** — and
`allocation_service.allocate_stage_work` **refuses** under the live default
`LEDGER_CREDIT_AT_ALLOCATION=False` (`allocation_service.py:69`). So at complete-time
there is **nothing to draw the pool down into**. → S4's `WorkerStageAllocation` cannot be
`StageWorkAssignment`; it must be a **new model born at complete**, distinct from the
settlement earning line. The addendum names `WorkerStageAllocation` but never reconciles
its **timing** against settlement-first SWA. This is the deepest design gap — resolve the
allocation source-of-truth (new pre-settlement allocation row → its relationship to the
finalize-time SWA) **in the design before any S4 code**.

## B. Current data-integrity hole (exists in S3, will corrupt the S4 pool)

**H1 — Cutting `color_id`/`size_id` are `required=False` → mixed grain within one stage (M1-5, MEDIUM, upheld).**
`cutting/handler.py:91,94` mark color/size optional; `report_contributions` does not
require them. A single Cutting stage can therefore hold both `(Red,M):50` and
`(NULL,NULL):30` rows. M-1's "each stage has ONE grain" + the pool's
`filter(color=…, size=…)` aggregation assume uniform grain. Mixed rows break it.
**Change:** before S4 builds the pool, decide — make color/size **required** on grain-
declared stages (DB check), or make S4's aggregation explicitly tolerate the NULL bucket.
This is the one finding that is a real property of *shipped* data, not just unbuilt S4.

## C. Design items S4 must pin (not contradictions — unresolved specifics)

- **D1 (M1-1/M1-2):** `allocation_dimensions` + per-handler grain declaration + the
  grain-monotonicity ("may only coarsen downstream") flow-editor check are **unbuilt**.
  This is S4's *first* task, not a foundation defect — but the monotonicity check must
  exist before any pool composes across stages.
- **D2 (M3-3, the one real M-3 item):** pin the `StagePoolSnapshot` lock predicate —
  lock the SPS row by `stage_record_id` (in-memory) **without** locking `AddaStageRecord`.
  This is the single discipline that keeps the production-truth and settlement lock
  domains disjoint. With it, **no deadlock** (M3-2/M3-4/M3-5 all refuted — see §E).
- **D3 (M2-3):** define the pool's "good" **source at coarse (non-cutting) stages** —
  `WorkerStageContribution.good_quantity` at WSC grain vs `AddaStageRecord.
  cost_quantity_snapshot` at SR grain. The addendum says `snapshot.good`; "good" is not a
  field on any snapshot table today.

## D. M-4 reopen contract — partially shipped; complete it WITH S4 (GO-WITH-CHANGES)

`reopen_stage_record` (`_shared.py:116-133`) refuses only on **settled** earnings (era-B).
The addendum's M-4 — "refuse upstream reopen when any downstream consumer exists: a
`WorkerStageAllocation`, a good/alter/missing contribution, or AlterCase" — is **not
implemented** for era-A (M-4-1/M-4-2/M-4-5, upheld). After S3, good/alter/missing data

stages** (some use `downstream_started_guard`, Cutting's path differs — M-4-3, upheld).
**Current risk is LOW** (nothing consumes the upstream→downstream good relationship until
the S4 pool exists), but it is a locked-contract gap. **Change:** the era-A reopen guard
(refuse on downstream `WorkerStageAllocation` + downstream completed good/alter/missing)
**must land in the same sprint as `WorkerStageAllocation`.** Optional now: a soft over-
draft warning in `save_draft_contributions` (M-4-4 was **refuted** as a current defect —
correctly deferred).
