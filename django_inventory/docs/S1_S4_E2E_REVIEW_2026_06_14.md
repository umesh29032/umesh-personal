# S1–S4 Foundation — Browser E2E Review (2026-06-14)

Step 3 of the validation sequence. Headless-browser pass (gstack) over the corrected
foundation (post F1–F4), super-admin login, on the dev DB (migrations 0037–0042 + expense

- **Login + role-based landing** — super-admin → Operations dashboard (P1-1). Sidebar order
  Main→Production→Raw Materials→Storefront→Tracking→Payroll→Admin (P1-2). No JS console errors.
- **Adda list / detail** — hero, status, stage tabs, activity, history render clean.
- **🆕 Super-admin "Stage Rates" link** on Adda detail (the new S1.1 mount) — present + gated.

  - **mobile (375px): clean** stacked cards, all 3 role rows, touch-friendly CORRECT buttons.

## Findings

### 🔴 Critical — NONE
The critical money-safety defect was the rerate↔finalize race, already caught + fixed (F1).
The browser pass surfaced **no new Critical**.

### 🟠 Important before production
- **I-1 (sequencing, = S5):** M-6 reconciliation is **WARN-only**, not a hard finalize BLOCK.
  Settling an over-allocated Adda only warns today. The BLOCK + tolerance + audited override is
  **S5** — so *proceeding to S5 is what resolves this*. Not a code defect; the planned next step.
- **I-2 (S5 rollout safety, = S4-005):** enabling `ENFORCE_ALLOCATION_BOUND` later has no
  operator pre-check / draft soft-warn — a flip could fail completions with no preview. Must land
  **with S5's rollout** (soft-warn + a "preview unallocated completions" utility) before the flag
  is ever flipped on. Flag is default-off, so not a pre-deploy blocker.

### 🟡 Nice-to-have / future-fit (the manufacturing-flow context)
- **N-1 — Adda-level cost-method / stage-behavior control does not exist.** `cost_method`
  (per-layer/fixed/per-piece) + `credits_workers` are configured **per-product** (flow editor)
  and frozen onto the Adda. Per-Adda, only the **rate** is overridable (the new rerate UI). When
  the factory needs per-Adda variation of the *method* or *behavior* (not just rate), that
  surface isn't there yet. Today: product-level config + per-Adda rate correction — likely
  enough for launch. *Future:* an "Adda stage config" surface. (Allocation/cost/earning/
  settlement stay independent — verified; this is about per-Adda override granularity.)
- **N-2 — `allocation_dimensions` (pool grain) has no UI.** `set_stage_grain` is service-only,
  seeded from the handler. Inert today (pool has no consumer). When a piece-consuming stage
  (stitching) is added, grain needs a flow-editor control. Tie to pool activation (post-stitching).
- **N-3 — stage-rates list lacks costing context.** Shows rate + locked/settled, but not the
  stage's `cost_method` or grouped status (a grouped stage shows ₹0 with no "paid at Cutting"
  hint). Adding a method + grouped badge would make the correction screen self-explanatory.
- **N-4 — "Stage Rates" is a small underlined hero link;** a clearer button would aid discovery.
- **N-5 — "0 earning lines recalculated"** is accurate but can read as "did nothing"; showing
  the per-role completed-contribution count on the list would set expectations before correcting.

## Scope note
The browser pass focused on the **new** surface (rate-correction) + the **costing-config** and
**settlement** surfaces (the future-fit + money-relevant ones). The existing worker→assign→
report→complete→reopen→settle clicks were NOT re-driven in the browser — they're covered by the
630-test suite + the byte-identical golden ₹225 chain. Targeted browser validation, not a full
re-click of every existing flow.

## Recommendation: ✅ GREEN to start S5
The foundation is browser-validated and sound — F1–F4 fixed, golden byte-identical, no new
Critical, the new UI works end-to-end (incl. mobile). The two "before production" items are
**S5 itself** (I-1 = the BLOCK) and **S5's rollout safety** (I-2 = soft-warn + pre-check). So
the right next move *is* S5 (built flag-off): it delivers I-1 and must include I-2. The
future-fit items (Adda-level costing override, grain UI) are post-S5 / post-stitching, not S5
blockers. **Proceed to S5** (M-6 finalize BLOCK behind a flag, default WARN) + fold S4-005 into
its rollout scope. S6-reversible after; the irreversible DROP stays post-deploy.
