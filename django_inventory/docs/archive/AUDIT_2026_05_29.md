# Application Audit — 2026-05-29

Read-only audit. No code changes. Findings only.

**Scope:** models, services, views, templates, RBAC, forms, tracking, URLs, docs.
**Method:** 6 parallel Explore agents across subsystems.
**Verdict (TL;DR):** Solid foundation. Architecture is mature, RBAC ~99% clean, services well-bounded, mobile patterns present. Main debt sits in 4 service-boundary violations (cutting_pattern + ProductSize), missing composite indexes for dashboard queries, denormalized counters without invariant tests, and storefront/inventory forms that skip the form-shell pattern.

Use this report to **pick the next 5-10 issues to ship**. Each finding has file:line ref so a follow-up PR can be scoped tight.

## 1. What's Already Good

Concrete patterns worth keeping + scaling:

- **Service-layer discipline** (CLAUDE.md rule 4) — `StockService.log` is single writer to `StockLedger`. No signals. `transaction.atomic` consistent in stage services. `select_for_update()` on `Product.adda_counter` race-safe.
- **Activity timeline service** (`config/production/services/activity_service.py`) — named-tuple + UNION-style aggregation from 4 sources. Single source of truth for "who did what".
- **Access service** (`config/production/services/access_service.py:36-73`) — defense-in-depth: Super Admin + Manager hardcoded bypass + DB-driven role/skill lookup.
- **Permission service** (`config/inventory/services/permission_service.py`) — curated section role editor (line 383), Super Admin bootstrap bypass (lines 122-126), sidebar predicate-gated (lines 159-256).
- **History service** (`config/tracking/services/history_service.py`) — three single-writer functions; audit trail guaranteed consistent.
- **Lazy barcode creation** (`config/tracking/services/barcode_service.py`) — `BarcodeBatch` stores range; per-piece `BatchBarcode` rows lazy-created on first scan. 500-piece Adda = 1-5 batch rows not 500.
- **Deterministic barcode allocation** — ranges aggregated by `(size, color, display_order)`, reruns produce identical output. Idempotent via `get_or_create` inside `@transaction.atomic`.
- **Atomic Adda counter** (`config/production/services/adda_service.py:86`) — `Product.objects.select_for_update()` locks counter row.
- **Snapshot pattern** — `LayeringRecord.rolls_used` M2M captures roll state at completion. Future roll edits don't corrupt history.
- **Draft state on AddaStageRecord** (`draft_*` fields) — generic across stages, form survives navigation, cleared on completion.
- **Per-product library pattern** — `ProductSize` per-product (TSHIRT S/M/L vs PANTS 28/30/32), patterns global but assigned via `ProductPatternAssignment` through-model.
- **CSS scoping discipline** — `adda_detail.html` scoped under `.adda-detail`, `barcode_dashboard.html` under `.bc-dash`, `roll_list.html` under `.roll-list`. Rule 10 mostly followed.
- **DataTables helper** — `initFancyDataTable()` in `base.html` centralizes DOM detach fix. 11 list templates reuse cleanly.
- **Filter chips with remove URLs** (`raw_materials/roll_list.html:42-65`) — backend builds remove URLs. Excellent multi-filter UX.
- **Mobile table card stacking** (`production/_stage_panel_cutting.html:67-79`) — `display: block` + `data-label` at 720px. Gold standard, replicate everywhere.
- **Hinglish "why" comments** — every model/service file opens with `YEH FILE KYU HAI?` naming the Django/PG primitive. Junior-friendly. Consistent.
- **Allauth restricted to pre-provisioned users** (`config/accounts/allauth_adapters.py:27-65`) — `SOCIALACCOUNT_AUTO_SIGNUP = False`, social signup blocked unless email already in DB.
- **Self-lockout + last-admin protection** (`accounts/views.py:305-321, 343-347`) — can't demote self or delete last Super Admin.
- **Argon2 + dual-axis throttling** (IP + email, per-endpoint windows) on all auth endpoints. 21 tests passing.
- **Production settings hardening** — HSTS 1yr, preload, SECURE_SSL_REDIRECT, SECURE_HSTS_INCLUDE_SUBDOMAINS, CSRF_COOKIE_SECURE, SESSION_COOKIE_SECURE, X_FRAME_OPTIONS=DENY.
- **ARCHITECTURE.md as living contract** (§0: "code wins, open PR to update doc") — uncommon clarity.
- **74/74 production tests green** per memory.

## 2. What Needs Improvement (Ranked by Severity)

### 🔴 CRITICAL — Service Boundary Violations

CLAUDE.md rule 4: views must call services for multi-row writes.

- **`config/production/views/product_views.py:138`** — direct `ProductSize.objects.create()` in view POST handler.
- **`config/production/views/product_views.py:148-165`** — multi-row `.update()` for add/update/archive/reactivate. No `transaction.atomic` wrapper on POST handler.
- **`config/production/views/pattern_stage_views.py:407`** — direct `CuttingPatternRecord.objects.create(stage_record=sr)` in `PatternVerifyView.post()`. Service `save_pattern_record()` already exists at `cutting_pattern_service.py:262` with `get_or_create` + atomic.
- **`config/production/views/pattern_stage_views.py:488`** — same pattern in `PatternSetSizesView.post()`.

**Impact:** Untracked CuttingPatternRecord creation (no history log). Partial writes possible mid-form. **Fix:** create `product_size_service.py` (add/update/archive/reactivate) + reuse existing `save_pattern_record()` in pattern stage views.

### 🔴 CRITICAL — Migration 0017 Destructive Without Data Path

- **`config/production/migrations/0017_alter_cuttingbundle_options_and_more.py`** — drops `count`, `color`, `pattern` fields from `CuttingBundle`. Restructures to header-only (count → `total_pieces` denormalized).
- No reverse migration. No data migration. **If production data exists, it's gone.**

**Fix before merge:** verify no prod data on `CuttingBundle` OR write data-preservation script + reverse path.

### 🔴 CRITICAL — Denormalized Counters Lack Invariant Protection

- **`CuttingBundle.total_pieces`** = SUM(items.count), recomputed by service. No trigger.
- **`CuttingPieceBreakup.consumed_count`** — manual service updates. Stale if `CuttingBundleItem` row deleted outside service layer.
- **`Product.adda_counter`** — service-safe via `select_for_update()`, but no DB constraint.

**Fix:** add invariant test (`recompute == stored`) on every mutation path. Long-term: PostgreSQL trigger or `pre_delete` recompute hook (or — better — never delete, soft-archive).

### 🟠 HIGH — Missing Composite Indexes for Dashboard Queries

Will bite at 40+ concurrent users.

| Model | Query | Missing Index |
|---|---|---|
| `BatchBarcode` | filter by `adda__product` + `status` | `(adda__product_id, status)` composite |
| `ClothRoll` | filter by `adda__status` | `(adda__status)` |
| `CuttingPieceBreakup` | yield analysis by `cutting_record__adda` | `(cutting_record_id)` ← FK index auto-created but not composite |
| `LayeringRollEntry` | per-Adda roll timeline | `(stage_record__adda_id)` |
| `AddaStageRecord` | timeline by product + `started_at` | `(adda__product_id, -started_at)` |
| `RemainingClothOfClothRoll` | leftover dashboard sorted by `remaining_length_meters` | `(is_consumed, remaining_length_meters)` |

**Fix:** add `Meta.indexes` with `models.Index(fields=[...])` per model. One migration. Cheap win.

### 🟠 HIGH — Form Shell Pattern Skipped on Storefront + Inventory

Memory `feedback_ui_polish.md`: user rejects basic Django forms.

- **`config/storefront/templates/storefront/listing/product_form.html`** — no `.panel` wrapper, no `.panel-num`, no sticky-actions. Uses bare `<section>` with **unscoped CSS** (66 `!important` instances across codebase, several here). CSS bleeds to other pages using `<section>` tag.
- **`config/storefront/templates/storefront/listing/category_form.html`** — minimal form. No hero, no panels, no sticky.
- **`config/inventory/templates/inventory/product_form.html`** — no form-shell. Hardcoded inline styles. No sticky-actions.
- **`config/production/templates/production/pattern_form.html`** — missing sticky-actions.
- **`config/production/templates/production/adda_form.html`** — chip pickers ✓ but no sticky action bar.

**Fix:** wrap each in `.form-shell` template include with `{% block panels %}` slots. Eliminates 5 forms of duplicated inline styling.

### 🟠 HIGH — Soft-Delete Flags Without Global Filter

`is_active` exists on `ProductPattern`, `Stage`, `ClothType`, `ClothColor`, `StorageLocation` — but **no model-level default queryset filters it**.

**Impact:** archived patterns/types leak into dropdowns. Stale stages appear in access rules.

**Fix:** add `ActiveManager` per model: `objects = ActiveManager()` + `all_objects = models.Manager()` (escape hatch for admin). Audit every form choice queryset to use `.filter(is_active=True)` until manager swap is safe.

### 🟠 HIGH — Template Leak: Raw `is_superuser`

- **`config/production/templates/production/product_list.html:13`** — `{% if request.user.is_superuser or current_role_code == 'super_admin' %}`. CLAUDE.md rule 6 violation.

**Fix:** add `can_add_product = user_has_role(user, {ROLE_SUPER_ADMIN})` in view context, use `{% if can_add_product %}` in template.

### 🟡 MEDIUM — Empty State UI Missing

19 list pages use inline `<tr><td colspan="...">No rows yet...</td></tr>`. Only 6 use `.empty-state` component class. No standard empty-state card.

**Fix:** add `.empty-state` card + `.empty-state-row` table variant to `base.html`. Refactor in subsequent PRs (low risk, high consistency win).

## 4. Scalability Concerns

- **`BatchBarcode`** — grows O(pieces × Adda count). 500-piece × 1000 Addas/yr = 500K rows in year 1. Index gaps make `status` scans expensive. **Mitigation:** monthly partition on `created_at` once table > 1M rows.
- **`ClothRollHistory`, `AddaHistory`** — append-only audit. Same partition candidate. Always queried with `ORDER BY -created_at` — index already correct, but full table scans on history dashboards likely.
- **Concurrent scanning** — `scan_piece` view not wrapped in `@transaction.atomic` (only `get_or_create_piece` is). Race window between get_or_create and last_scanned_at update. Low probability, no FK lock, but a concurrent delete during scan could 500.
- **`ProductSize` archive churn** — multi-row write in view (not service) increases lock window during edits. At 40 concurrent users editing different products, fine. At 40 editing same product, contention.
- **No connection-pool config visible** — Django default = 1 conn per request. At 40 concurrent users + slow queries = exhausted pool. Verify `CONN_MAX_AGE` + pgbouncer.

## 5. Future Maintenance Concerns

- **Denormalized counters without invariant test** = bug ticking. When a future PR forgets to call the service, counters drift silently. **Add `recompute_and_assert()` smoke test in CI.**
- **Cutting flow has 5 models with deep FK chains** (CuttingPatternPhoto → CuttingPatternRecord → AddaStageRecord → Adda → Product). Refactor friction high if business rule changes (e.g. multi-product Adda).
- **4-way `unique_together` on `CuttingPieceBreakup`** is a smell. Likely needs a `BreakupKey` value object or normalized `PatternColorSize` lookup table.
- **ProductPattern.is_active soft-delete vs ProductPatternAssignment hard reality** — archive a pattern, but assignments still PROTECT it. No clean retirement flow.
- **No root `README.md`** — new dev has no entry point. ARCHITECTURE.md is good but assumes you know to read it.
- **`ABOUT_THIS_PROJECT.md` stale** — 2026-05-16, pre-pattern-reopen work. Either update or remove.
- **Migration 0017 reverse path** — if you ever need to roll back, you can't.

## 6. Architecture Risks

- **Adda.current_stage acts as state flag** — NULL means COMPLETED. Disguises state as nullable FK. Explicit `status` field exists (`Adda.status` TextChoices) — consolidate, mark current_stage non-null while in-progress.
- **Pattern stage views bypass existing service** (lines 407, 488). Service exists, view doesn't use it. Symptom of incomplete refactor during PR8.
- **Service return shapes mixed** (object vs dict vs list vs int) — fine if intentional, but document in `services/__init__.py` docstring.
- **Iframe-based stage panel** (`adda_detail.html:609`) — works for CSS isolation but couples parent/child via postMessage. Future stage additions may need same pattern; consider extracting reusable embed helper.
- **No feature-flag system** — adding "machine tracking" or "QC" will require global rollout. Consider lightweight `django-waffle` or settings-based gates.

- **`ProductSizesEditView.post()`** lacks outer `@transaction.atomic` — partial mid-form failures persist.
- **`scan_piece` view** not atomic (acceptable currently, see Scalability).
