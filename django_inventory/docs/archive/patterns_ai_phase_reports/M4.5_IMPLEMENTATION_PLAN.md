(2026-07-10 · PLAN ONLY, no code until owner approval · designed from
the real factory workflow — the physical half-pattern, the folded lay,

## §0 · WHAT FOLD IS IN THE FACTORY (the design's foundation)

The cutting master's fold is fabric physics, not geometry math:

1. The CARDBOARD is a HALF-PATTERN. The Nickar Body template on the
   table is half the body; one straight edge of it is the FOLD LINE.
2. The FABRIC must offer a FOLDED EDGE at that line. Only some lays
   do: fold the fabric lengthwise and the crease is a fold edge; lay a
   knit TUBE flat and BOTH sides are fold edges; lay open fabric
   single or as two loose plies and there is NO fold edge anywhere.
3. The master places the half-pattern's fold line ON the fabric's
   folded edge, cuts around the rest, opens it — ONE symmetric full
   piece. Half the marker space, one placement, guaranteed symmetry.
4. When there is NO folded edge, the master UNFOLDS the pattern:
   traces the half, flips it about the fold line, traces again — a
   full outline, cut like any normal piece.

Every design decision below is one of these four facts, digitized.

## §1 · THE NINE OWNER QUESTIONS — ANSWERED FIRST

**Q1 · Which pattern types can legally use a fold?**
Any piece whose Blueprint says `on_fold=True` AND whose geometry
carries a marked FOLD EDGE (a straight outline segment). That is the
whole law — data, not garment types. Body-on-fold for a Nickar, back
panel for a polo, front for a school-uniform shirt: same two flags.
Blueprint advisory (never blocks): `on_fold + is_pair` flagged as
contradictory — a fold piece is symmetric by construction, a pair of
it is just two of it.

**Q2 · How is the fold line represented in geometry?**
The TRUTH stays the physical object: we store the HALF-PATTERN (what
the Studio digitizes — the cardboard that exists), with the fold line
as typed metadata in the canonical payload's RESERVED slot:
`features.fold_edge = {'p1_um': [x,y], 'p2_um': [x,y]}` — two
vertices of the outline bounding one STRAIGHT outline segment.
Validator twins (lockstep) enforce: both points are outline vertices ·
the segment between them is straight and unbroken · present only when
declared. This is **adr-c.3** — the third conscious contract bump; the
stamp machinery does the rest; every c.2 payload stays valid (slot
optional).
The OPENED (unfolded) outline = half + its mirror about the fold line
— **DERIVED AT READ, NEVER STORED** (the standing law). Facade rows
gain `opened_dims`/`opened_outline` derived fields; tape verification
keeps measuring the HALF (the physical object on the table).

**Q3 · How do the lay types affect fold placement?**
The lay's FOLD-EDGE COUNT becomes explicit data (recorded in the
Marker Plan → layout params, exactly like the multiplier):

| Lay (plan input) | plies/layer (M4 mult) | fold edges | fold placement |
|---|---|---|---|
| single, open | 1 | 0 | impossible → piece UNFOLDS (opened outline placed, cut 1) |
| double, open (2 loose plies) | 2 | 0 | impossible → UNFOLDS (cut 2 opened) |
| double, folded lengthwise | 2 | 1 (one side) | ON the folded side |
| tubular | 2 | 2 (both sides) | ON either side |

M4's `double` splits into `double_open` / `double_folded` (the factory
distinguishes them with its hands; the plan dialog now asks). M4
compatibility: existing `double` params read as `double_open`
(multiplier semantics identical — byte-identical legacy math).

**Q4 · How does fold change placement count?**
One clean formula, extending M4's G3 without touching it:
**pieces-per-placement = on-fold-placement ? multiplier ÷ 2 : multiplier.**
- double_folded (mult 2): fold placement opens across the crease →
  **1 piece** per placement per laid layer; normal piece → 2.
- tubular (mult 2): same — fold placement 1, normal 2.
- single (mult 1): no fold edge; the UNFOLDED outline cuts 1 — the
  formula never runs (no fold placements exist on these lays).
Queue math: required placements = ceil(count × garments ÷
pieces-per-placement) — per PIECE now, not per lay. The queue chip
says it in factory words: "on fold — opens to 1/layer".

**Q5 · How does fold interact with mirror pieces?**
It doesn't — by physics. A fold piece is symmetric; mirroring it is
identity. DCT: mirror DISABLED for fold placements ("symmetric piece —
the fold IS the mirror"). Unfolded fallback outlines are symmetric
too; mirror stays disabled. `is_pair` on-fold combos = the Q1
Blueprint advisory.

**Q6 · Recipes + Import Queue effects?**
Recipe stores the refined lay vocabulary (double_open/double_folded) —
one new choice value, zero model changes (JSON/choices additive).
Queue consumes Q4's per-piece math. Import of an on-fold piece on a
fold-capable lay enters FOLD PLACEMENT (Q8); on a fold-less lay it
imports the derived opened outline with the honest chip "no folded
edge on this lay — piece unfolded". Over-import law unchanged.

**Q7 · How will AI suggest fold usage without touching geometry?**
Three containments, all existing laws:
1. The engine NEVER sees fold geometry decisions: fold placements go
   to the optimizer as **fixed obstacles** (exactly the locked-piece
   mechanism that already exists) — they slide only along their edge
   (v1: fully fixed during suggestion).
2. Fold-usage advice = a DISPLAY-ONLY advisory chip, derived from
   data: piece.on_fold ∧ lay.fold_edges>0 ∧ piece imported unfolded ⇒
   "This piece could sit on the fold — half the space." Never applied,
   never a gate — the M8-C advisory doctrine.
3. Geometry untouched forever: fold_edge is written only in the Studio
   (single writer); the DCT/AI read it.

**Q8 · How does the DCT visually represent fold edges?**
The FABRIC shows its folded edge(s): a distinct dashed edge-line along
x=0 (double_folded) or both sides (tubular), labeled "FOLD". A fold
placement renders the HALF outline SNAPPED to that edge (its fold
segment coincident with the fabric fold line) + the marker-table
convention: a fold glyph on that edge + an "on fold" label chip. Drag
= 1-D along the edge (x pinned); pulling it off the edge = new
violation paint class `col-fold` (violet family — the boundary color's
sibling) with the honest hint "fold pieces live on the folded edge".
No mirrored ghost across the edge — the other half is the UNDER PLY,
not more marker space; drawing it would lie about fabric consumption.

**Q9 · How do future garments reuse this with zero code?**
Every mechanism above consumes ROWS: `on_fold` (Blueprint) +
`fold_edge` (geometry payload) + lay fold-edge count (plan input).
A hoodie back-on-fold, a polo front, a school-uniform pinafore — all
just Product Definitions. The M4 GENERICITY GUARD test extends over
all new code automatically; the fold logic contains no garment
vocabulary by construction.

# REVISION 2 — PATTERN CAPABILITIES (owner refinement, 2026-07-10)

## R2-§1 · THE HONEST VERDICT ON THE CRITIQUE

**Where the design was already equivalent — precisely:**
The plan never made fold a layout property. Q1's law is Blueprint
`on_fold` + geometry `fold_edge` — both PATTERN-owned, written only in
the Studio, read by the DCT. The LAY only answers "is the capability
USABLE here?" (fold edges exist on this fabric), exactly as rotation
already works: `grain_rule` lives on the pattern; the lay (one-way
nap) narrows how it may be USED. Capability = pattern's, usage =
layout's — that philosophy was §1's spine.

**And the capabilities VOCABULARY already exists as data, one field
per capability, all pattern-owned (M4 review §3 catalogue):**

| Capability | Where it lives today |
|---|---|
| Supports Fold | `on_fold` (Blueprint) + `fold_edge` (geometry, M4.5) |
| Supports Mirror / Pair | `is_pair` |
| Supports Rotation / Grain | `grain_rule` + `features.grain` |
| Seam | `seam_allowance_mm` |
| Notches | `expected_notches` + `features.notches` |
| Cut count | `pieces_count` |
| Mandatory/Optional | `is_optional` |

**Why NO new Capabilities table:** a `PatternCapability` model would
duplicate these seven fields into a second store — two writers, two
truths, drift risk, and a violation of the owner's own
anti-over-engineering and fit-existing-architecture laws. The concept
is right; the storage already exists. What was MISSING is the NAME —
consumers read scattered fields instead of one contract. Fixed below.

## R2-§2 · THE THREE ADOPTED REFINEMENTS

**A · The Capabilities contract (named, one place).**
The facade design row gains ONE derived dict — the formal Pattern
Capabilities contract every consumer reads (DCT payload, queue, M6,
M7, every future surface):
```
capabilities: {
  fold:     on_fold AND geometry has fold_edge,   # usable, not just wished
  mirror:   is_pair,
  rotation: grain_rule,          # strict | two_way | free
  pair:     is_pair,
  seam_mm:  seam_allowance_mm,
  notches:  expected_notches vs actual (advisory),
  count:    pieces_count,
  optional: is_optional,
}
```
Derived at read from the existing fields (single truth, no migration,
no second writer). The DCT payload ships `capabilities` instead of
loose flags — the queue, placement gates and future consumers speak
ONE vocabulary. Blueprint stays the ONLY capability editor.

**B · Import PLACEMENT MODES (the owner's UX — adopted verbatim).**
The DCT never asks "can this fold?" — the Library answered already.
The queue row of a fold-capable piece on a fold-capable lay offers the
INSTANCE decision, exactly like the cutting table:
```
Nickar Body   req 2 · in 0 · fold-capable
              [ Import on fold — opens to 1/layer ]
              [ Import normally — cuts 2/placement ]
```
On a fold-less lay: one button, "Import (unfolded) — no folded edge on
this lay". Placement mode = per-instance, recorded on the placement
(`on_fold: true/false`), Q4 math per mode. This REPLACES the plan's
auto-fold-on-capable-lay behavior — the operator decides HOW to place,
never WHETHER the pattern can. (Both-mode markers are real factory
practice: one Body on the fold + one open when the ratio is odd.)

**C · The Studio INFERS the capability — proposed once, confirmed
once, owned forever.**
At draft review/confirm, a DETERMINISTIC geometry check (no ML —
rule ⑩): find straight outline edges; mirror the outline about each
candidate; measure the match. Two proposals, both one-shot advisory:
- Blueprint says on_fold but no edge marked → "Fold edge detected
  along the left edge — accept?" (pre-marks the best candidate; the
  expert accepts/adjusts/rejects).
- Blueprint says nothing but the outline shows strong bilateral
  symmetry about a straight edge → advisory chip "This piece is
  symmetric about a straight edge — mark as fold-capable?" One click
  = `on_fold` + `fold_edge` set (through the single writers). Asked
  ONCE; the answer is permanent pattern knowledge (reference vs
  geometry separation: capabilities derive from evidence ONE time,
  at verification — never re-derived).
Confidence shown display-only (the standing law). Refusals/rejections
recorded. v1 boundary (honest): the detector is a symmetry+straightness
check, not shape understanding; it PROPOSES, the expert owns the
answer.

# REVISION 3 — THE THREE CONCEPTS (owner-requested clarification, 2026-07-10)

Future contributors: these are DIFFERENT things. Never merge them.

**1 · PATTERN CAPABILITY — permanent pattern knowledge.**
What the piece CAN do, forever, everywhere. Lives on the pattern
(Blueprint fields + geometry payload features), written ONLY in the
Studio/Blueprint through the single writers, established once at
verification. Examples: supports fold (`on_fold` + `fold_edge`),
mirror (`is_pair`), rotation (`grain_rule`), seam, notches, count,
optional. Exposed to every consumer as the derived `capabilities`
contract (R2-A). A capability never changes because of a layout.

**2 · PLACEMENT MODE / STRATEGY — a per-placement decision inside one
layout.** HOW this particular instance uses a capability, decided by
the operator at import ([Import on fold] / [Import normally]),
recorded ON the placement (`on_fold: true/false`), affecting only this
layout's math and visuals. Marker Recipes may PRESET such decisions —
they are saved plans, never new capabilities.

**3 · LAY CAPABILITY — properties of the current cloth/roll/lay.**
What THIS fabric setup offers: plies per layer (multiplier), fold
edges (0/1/2), one-way nap, usable width, stretch. Lives on the roll
(raw_materials data) + the Marker Plan (recorded into layout params).
A lay capability can make a pattern capability UNUSABLE here (no fold
edge ⇒ unfold; one-way nap ⇒ no flips) — it can never create one.

Rule of thumb: **the pattern owns what CAN happen · the lay owns what
is POSSIBLE today · the placement owns what the operator CHOSE.**
