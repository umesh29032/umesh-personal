# 05 — SELECT Basics

> Part of [SQL From Zero](00_COURSE_OVERVIEW.md). Prev: [04](04_NULL.md) · Next: [06 — Filtering & Expressions](06_Filtering_And_Expressions.md).

# Learning Objectives
By the end of this chapter you can:
- write SELECT / FROM / WHERE / ORDER BY / LIMIT from memory
- recite the logical execution order and use it to explain an alias error
- say why row order is undefined without ORDER BY
- explore any table safely, knowing SELECT changes nothing

# Purpose
To learn the one verb you will use 95% of the time — and to learn it *properly*,
including the execution order that explains half of all beginner SQL errors.

# The Problem
"Show me the Addas that are finished, newest first, just the code and status."
Until I can express that in SQL, I am reading data through screens somebody else
built. `SELECT` is how I ask my own factory a question directly.

# Theory (from zero)
The full anatomy — memorise this skeleton:

```sql
SELECT code, status          -- 3. WHICH columns to show
FROM production_adda         -- 1. from WHICH table
WHERE status = 'completed'   -- 2. keep only rows passing this test
ORDER BY id DESC             -- 4. sort (DESC = biggest first, ASC = default)
LIMIT 5;                     -- 5. at most 5 rows
```

**The numbers are not decoration.** SQL is *written* in one order and *executed*
in another. Postgres thinks:

**FROM** (fetch the table) → **WHERE** (throw away rows) → **GROUP BY** → **HAVING**
→ **SELECT** (keep asked-for columns, compute aliases) → **ORDER BY** (sort what
survived) → **LIMIT** (cut).

That single fact explains a classic error: an alias you invent in `SELECT` cannot
be used in `WHERE`, because WHERE ran *before* SELECT existed. But `ORDER BY`
*can* use it — it runs after. Try it and see (Practical below).

Other essentials:
- `SELECT *` = every column. Convenient for exploring, sloppy in real code.
- `AS` names a column in the output: `SELECT sum(amount) AS total`.
- `DISTINCT` collapses duplicate rows: `SELECT DISTINCT status FROM …`.
- `count(*)` counts rows — the fastest "how big is this?" question.
- Whitespace and line breaks mean nothing to SQL; the semicolon ends the statement.
- **`SELECT` never changes data.** It is always safe to run, anywhere, including
  on `inventory_db`. This is why exploring is free.

> 💡 **Samjho aise:** SELECT ek **chhalni** hai. FROM = kaunsa dabba kholna,
> WHERE = kaunse daane rakhne, SELECT = har daane ka kaunsa hissa dikhana,
> ORDER BY = kis tarah lagana, LIMIT = bas itne hi. Chhalni dabbe ko **kabhi
> badalti nahi** — isi liye poochhne mein kuch nahi jaata.

# Real World Example (My ERP)
Every list screen in my ERP is a SELECT underneath. The Adda list, the worker's
"My Work" cards, the settlement table — Django writes the SQL, but it is this
shape. When a page shows the wrong rows, the fastest debugging move is to write
the SELECT by hand in dbshell and compare.

# Practical — try it yourself
```bash
env/bin/python config/manage.py dbshell --settings=config.settings.local
```
```sql
-- how big is this table?
SELECT count(*) FROM production_adda;                       -- 28

-- newest five, two columns (REAL output on my data):
SELECT code, status FROM production_adda ORDER BY id DESC LIMIT 5;
--     code     |   status
--  3-PATTI-018 | completed
--  T-SHIRT-004 | in_progress
--  NIKKAR-002  | in_progress
--  3-PATTI-017 | completed
--  3-PATTI-015 | completed

-- which distinct states exist at all?
SELECT DISTINCT status FROM production_adda;

-- aliases:
SELECT code AS adda, status AS state FROM production_adda LIMIT 3;

-- PROVE the execution order — this FAILS:
SELECT code AS adda FROM production_adda WHERE adda = '3-PATTI-018';
-- ERROR:  column "adda" does not exist
--   ^ WHERE ran before SELECT invented "adda"

-- but this WORKS (ORDER BY runs after SELECT):
SELECT code AS adda FROM production_adda ORDER BY adda LIMIT 3;
```

# Production Walkthrough
Every list screen in the ERP is one of these underneath:
- The Adda list is `SELECT … ORDER BY id DESC` with a page limit — the same five clauses you just learned, generated by the ORM (ch 16).
- **Pagination depends on a stable order.** Ordering by a non-unique column (say `status`) makes page 2 non-deterministic: a row can appear twice or never. Every paged query here orders by something unique.
- `SELECT *` never appears in application code — the ORM names its columns, so adding a field cannot break an existing page.

# Debugging Guide
"The page shows the wrong rows":
1. **Re-run the query by hand** in `dbshell` with the same WHERE. If it is wrong here, it is not a template bug.
2. **Remove the WHERE, add LIMIT 5.** Confirm the table has what you expect at all.
3. **Check the ORDER BY.** "The newest one is missing" is often "there is no ORDER BY".
4. **Count before you read.** `count(*)` with and without the filter tells you whether the filter or the data is wrong.

# Performance Notes
- `LIMIT` without `ORDER BY` is cheap but non-deterministic; with `ORDER BY` on an indexed column it is still cheap (the index is already sorted — ch 14).
- `SELECT *` costs extra I/O for columns nobody displays, and can defeat an index-only scan.
- `count(*)` on a huge table is not free in Postgres (MVCC — ch 18, 24); use it freely at this scale, cautiously at millions.

# Security Considerations
- `SELECT` cannot damage data, which is why exploring is encouraged — but it *can* **expose** it. A query that returns money columns to a page a worker can see is a leak even though nothing was written (the audit probed exactly this).
- Never build a WHERE clause by string-concatenating user input (ch 22).

# Architecture Decisions
- **Read paths stay in the ORM** so pagination, filtering and permissions are applied in one consistent place.
- **Stable ordering by a unique column** is a deliberate rule here, because "duplicate row on page 2" bugs are nearly impossible to diagnose after the fact.
- **Views never build raw SQL for lists** — the service/ORM boundary keeps access rules attached to the query.

# Best Practices
- Name your columns in real code; use `*` only while exploring.
- Always `ORDER BY` something unique when you `LIMIT`.
- Put a `LIMIT` on any exploratory query before you press enter.
- Read the execution order once a week until it is reflex.

# Beginner Mistakes
- Using a `SELECT` alias in `WHERE`. Impossible by design — see the error above.
- `SELECT *` in application code: fetches columns nobody needs, and breaks
  silently when a column is added or reordered.
- No `LIMIT` while exploring a big table — you pull millions of rows to your terminal.
- Forgetting the `;` and thinking psql has frozen. It is waiting for you.
- Assuming rows come back in a predictable order without `ORDER BY`. **Without
  ORDER BY, order is undefined** — Postgres may return them any way it likes.

# Interview Questions
- **Junior:** *What does `SELECT * FROM t LIMIT 10` do, and why avoid `*` in production?* — returns 10 rows of every column; `*` over-fetches and is fragile to schema change.
- **Junior:** *Difference between `count(*)` and `count(col)`?* — rows vs non-NULL values of that column (ch 04).
- **Mid:** *What is the logical order of execution of a SELECT?* — FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. **Extremely commonly asked**, usually as the trap: "why can't WHERE see my alias?"
- **Senior:** *Is row order guaranteed without ORDER BY?* — no, never; it depends on the plan, storage and concurrent activity. Relying on it is a latent bug.
- **Staff:** *Why is `LIMIT` without `ORDER BY` non-deterministic, and where does that bite?* — "top N" pages silently show different rows across runs; pagination needs a stable total order (typically an indexed unique tiebreak like `id`).

### Why interviewers ask these — and the answer that separates levels

| Testing for | Weak answer | What lands |
|---|---|---|
| Do you know the **logical** order of execution? | "It runs top to bottom: SELECT, FROM, WHERE." | **FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.** That is why `WHERE` cannot see a `SELECT` alias but `ORDER BY` can. Usually asked as exactly that trap. |
| Do you know `SELECT *` is a production smell? | "`*` is convenient and the DB caches it anyway." | It over-fetches (wide rows, more I/O, no index-only scan) **and** is fragile: adding a column silently changes what your code receives. Name columns. |
| Do you know row order is never free? | "Rows come back in insertion order." | **Never guaranteed** without `ORDER BY` — it depends on the plan, physical storage and concurrent activity. Today's "correct" order is tomorrow's bug when the planner switches strategy. |
| Can you spot the pagination trap? | "LIMIT 10 gives the first ten." | `LIMIT` without a **total** order is non-deterministic, so page 2 can repeat or skip rows. Pagination needs a **stable tiebreak** — typically an indexed unique column like `id` appended to the sort. |

**The killer follow-up:** *"Your 'top 10 workers' report shows different names on refresh. Why?"* — `LIMIT` on a non-unique sort with ties. If you cannot diagnose that in one sentence, every report you write is quietly unstable.

# Revision Notes
- `SELECT cols FROM t WHERE test ORDER BY c DESC LIMIT n;`
- Execution order: **FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT**.
- Alias usable in ORDER BY, **never** in WHERE.
- No ORDER BY = **no guaranteed order**.
- SELECT is always safe to run; it only reads.

# Cheat Sheet
- `SELECT cols FROM table WHERE test ORDER BY col DESC LIMIT n;`
- execution order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
- alias usable in ORDER BY, **not** in WHERE
- `DISTINCT` de-duplicates · `count(*)` sizes a table · `AS` names output
- no ORDER BY = no promised order · SELECT is always safe
